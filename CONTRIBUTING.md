# Contributing

Changes must preserve the boundary between the Arduino-backed core experiments
and the separately maintained astronomy experiments. Read
[README.md](README.md) and [docs/REPO_MAP.md](docs/REPO_MAP.md) before changing
firmware, XML generation, or experiment behavior.

## Development setup

Use Python 3.11, matching CI:

```sh
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-test.txt
```

Install `xmllint`, `arduino-cli`, `ripgrep`, and `shellcheck` separately. The
Arduino compile step may download the pinned board core and libraries.

## Core experiment changes

Edit `src/phyphox/*.phyphox.xml` and shared fragments under
`src/phyphox/includes/`. Do not hand-edit the matching root files in
`experiments/`.

After a source change:

```sh
make build
make check-generated
make validate
```

Review source and generated changes together:

```sh
git diff -- src/phyphox experiments
```

## Astronomy experiment changes

Files in `experiments/astronomy/` are hand-maintained and are not generated by
`scripts/build-phyphox.sh`. Each file must retain English root strings and
German and French translations.

Keep source-specific input handling separate from the common physical quantity
used by views and exports. Update
`docs/ASTRONOMY_EXPERIMENTS_COMPANION.md` when a measurement path, model, or
interpretation limit changes.

`owon_digital_multimeter-debug.phyphox` is an integration helper for the
multimeter transit path. Its filename does not indicate disposable output.

Run the focused runtime contracts while editing:

```sh
pytest -q tests/test_runtime_contracts.py
bash scripts/validate-xml.sh
```

## Firmware and protocol changes

Keep BLE UUIDs and active mode IDs aligned across:

- `experiments/phyphox_constants.json`
- `src/phyphox/*.phyphox.xml`
- `arduino/phyphox_ble_sense/phyphox_ble_sense.ino`

The supported target is the original Nano 33 BLE Sense, not Rev2. A claim for
another board requires a separate compile path and device evidence.

Preserve BLE polling, the 50 ms minimum notification interval, bounded config
reads, and `NaN` output for unavailable samples. Treat changes to the 20-byte
payload or config characteristic as compatibility changes.

## Documentation and assets

Document observed behavior separately from unverified hardware behavior. Check
every command, path, link, environment variable, and protocol value against the
repository.

Do not add screenshots or embedded assets without source and redistribution
provenance. Do not add private URLs, local paths, credentials, device
identifiers, caches, reference captures, or generated bundles.

The component license scope is unresolved. Do not change license claims or add
third-party material without maintainer confirmation.

## Validation

Run the full local entry point before opening a pull request:

```sh
make ci-local
git diff --check
```

`make ci-local` runs Ruff, pytest, XML validation, generated-file parity,
Arduino compilation, and the local security checks. If the complete command
cannot run, use the relevant individual targets and state exactly what was
skipped:

```sh
make lint
make test
make validate
make check-generated
make compile
make security
```

Hardware-affecting changes require a manual test on every board revision claimed
as supported. Record the board revision, Arduino core, library versions,
phyphox version, external circuit, and observed result.

## Pull requests

Describe:

- behavior changed
- source and generated files affected
- checks run and their results
- hardware tests performed or skipped
- protocol, data-format, or compatibility impact
- license or attribution impact
